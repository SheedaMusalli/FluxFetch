# FluxFetch OmniLink integration

OmniLink routes eligible launcher transfers across independent IPv4 adapters. Process presets cover Steam, Epic Games, EA, Ubisoft Connect, GOG Galaxy, Riot, Battle.net and the Rockstar service. Client versions may use separate download workers; add their executable names explicitly when needed.

Right-click the OmniLink tray icon and choose **Add launcher or app...**. Enter the downloader executable name, one per line, save, and wait up to two seconds. Additional names are stored in `%LOCALAPPDATA%/FluxFetch/OmniLink/launchers.txt`; presets remain enabled. Entries are executable names, not paths or commands. Generic workers such as `Agent.exe` and `Launcher.exe` are opt-in because unrelated apps can use those names. The tray tooltip lists detected processes.

Start OmniLink before starting a download: it redirects newly opened IPv4 TCP connections on ports 80 and 443. Existing connections, UDP/QUIC, IPv6 and other ports are not routed. A launcher that reuses connections may need its download or process restarted. No launcher or game is modified. Bandwidth gains depend on independent Internet connections and servers permitting concurrent downloads.

The main **Launcher network RX** metric uses an independent Windows ETW collector. It observes selected launcher receive traffic on IPv4/IPv6 TCP and UDP, including connections that existed before OmniLink started and traffic that bypasses the relay. **Routed payload** remains a separate relay measurement. Proxy upstream sockets are explicitly registered so the same transfer is counted once; its delivery back to the launcher is excluded. Process creation/exit times distinguish process instances when Windows reuses a PID. ETW session, event loss, decoding and process-query failures produce **Unavailable**, rather than a fabricated zero. Normal administrator elevation is required for observation as well as interception.

The overlay, tray and adapter menus consume the same published snapshot, measured using actual elapsed monotonic time over two approximately 500 ms samples. Adapter rows show routed payload plus **Adapter RX (all apps)** from interface counters; the latter is not presented as launcher speed. Link rates describe the LAN connection, not Internet throughput. Routing status distinguishes waiting, one measured link and multiple measured links; enabling the option alone does not prove aggregation. **Transferring** includes background requests, not just game downloads. Stream translation state is retained while its original socket exists, regardless of connection age.

For controlled live observation tests, build `cargo build --manifest-path integrations/omnilink/Cargo.toml --example verify_observer` and run `target/debug/examples/verify_observer.exe` as administrator, passing an absolute output-report filename. The diagnostic uses known local payloads to verify pre-existing IPv4/IPv6 TCP connections, IPv4/IPv6 UDP and proxy deduplication. It does not intercept or modify installed launchers. The DLL/runtime needed by the diagnostic is staged beside the example automatically. These tests establish byte observation behavior, not a speed gain on public launchers.

`npm run build:omnilink` builds and stages the Windows x64 helper, WinDivert runtime and licenses. The installer includes it automatically. Rust stable MSVC is required. Real launcher downloads with multiple physical adapters remain manual validation; compilation and tests do not prove every client version or protocol is compatible.
